Document Intelligence Service

A stateless, cluster-internal service that turns business documents into Markdown, typed tables and factual image descriptions. Files in, structured text out — nothing is stored, nothing is interpreted.

1. Purpose

What it is

The Document Intelligence Service is a single-purpose HTTP service. A caller posts one or more files to it; the service detects what each file actually is, runs it through the extraction path appropriate to that file type, and returns Markdown (plus typed table rows for spreadsheets, or a description for images) in one synchronous response.

It exists so that every consumer in the platform gets the same text out of a document. Rather than each application embedding its own PDF parser, its own spreadsheet reader and its own vision prompt — and drifting apart in what they produce — document understanding is solved once, behind one contract.

What it can be used for

  • Feeding documents to an LLM or agent. Markdown is the format language models read best. A PDF, a Word file and a web page all come back in the same shape, so downstream prompts do not need per-format handling.
  • Extracting figures from spreadsheets without losing precision. Numbers come back as JSON numbers, not as re-parsed display text — quantities, prices and dates survive the trip intact.
  • Making scanned documents searchable. Scanned PDFs go through OCR on the same path as digital ones; the caller does not have to know which it had.
  • Turning photographs into text records. Images are described in terms of what is visibly present — objects, markings, labels, printed text, materials, colours — so a photo can be indexed and searched alongside the documents it came with.
  • Batch ingestion. A mixed batch of up to 32 files is processed in one call, with results returned in request order.

What it deliberately does not do

These are design constraints, not gaps. They are what keeps the service small and reusable:

  • It renders no judgement. The service reports facts about a document, never meaning: no classification, no categories, no compliance verdicts, no scoring. Interpretation belongs to the calling application, which knows the business context.
  • It stores nothing. Bytes arrive, results leave, memory is released. There is no database, no blob container and no cache of document content — it must never grow into a document store.
  • It logs no document content. Filenames, sizes, file types and durations are logged; the text inside a document never is, at any log level.
  • It is not internet-facing. The service is reachable only from inside the cluster; there is no ingress.

2. The contract

One endpoint does the work: POST /v1/extract, multipart/form-data. Send N file parts named files, plus an optional hints part carrying JSON. The response is synchronous JSON: camelCase field names, lowercase enum values, null fields omitted.

curl -s http://document-intelligence:8090/v1/extract \
  -F "files=@invoice.pdf;type=application/pdf" \
  -F "files=@parts-list.xlsx;type=application/vnd.openxmlformats-officedocument.spreadsheetml.sheet" \
  -F "files=@component.jpg;type=image/jpeg"
{
  "files": [
    { "name": "invoice.pdf", "kind": "pdf",
      "markdown": "# Invoice 2026-041\n\nSupplier: Acme GmbH\n…",
      "warnings": [] },

    { "name": "parts-list.xlsx", "kind": "xlsx",
      "markdown": "## Sheet1\n\n| Part | Qty | Unit price |\n|---|---|---|\n| Filter glass | 200 | 3.75 |\n",
      "tables": [
        { "name": "Sheet1",
          "markdown": "| Part | Qty | Unit price |\n|---|---|---|\n| Filter glass | 200 | 3.75 |\n",
          "rows": [ ["Part", "Qty", "Unit price"],
                    ["Filter glass", 200, 3.75] ] }
      ],
      "warnings": [] },

    { "name": "component.jpg", "kind": "image",
      "imageDescription": "A close-up photograph of a cylindrical glass lens element with a violet-tinted coating.",
      "warnings": [] }
  ]
}

Note the two representations of a spreadsheet. markdown is for reading; tables[].rows is for computing — 200 is a JSON number and 3.75 is a JSON number, one table per sheet. Consumers that care about the figures should read rows and never re-parse the Markdown.

The failure model

A well-formed request always returns 200. A file that cannot be processed gets its own error entry inside that 200 — it never fails the other files in the batch, and it never fails the call.

LevelStatusWhen
Per file200 with error The file is corrupt, empty, of an unsupported type, over the size cap, timed out, or its engine failed.
Request400 problem+json The request is malformed: not multipart, no files parts, too many files, file parts totalling over the request cap, oversized hints.
Request503 + Retry-After The pod's in-flight byte budget stayed full for the whole queue window. The request is valid and safe to retry.

Per-file error codes: unsupported_type · too_large · empty_file · corrupt · timeout · engine_error · engine_unconfigured. The last of these stays in the frozen vocabulary but no running instance emits it: both cloud endpoints are required configuration, so a surface the service could not serve stops it at boot rather than surfacing per file (see Deployment shape under section 4).

Alongside errors, each file carries a warnings array for anything worth knowing that did not stop the extraction — a declared content type that disagreed with the actual bytes, a spreadsheet tab that was a chart rather than a worksheet, a single cell that could not be parsed as the number or date its own formatting claimed.

Stage by stage

StageResponsibility
Admission Reserves the request's byte cost before the body is read. This is what bounds pod memory: every accepted file is held whole in memory for the duration of the request, so without a ceiling, peak usage would be bytes-per-request × concurrent requests. A request that cannot get budget in time is shed with a retryable 503 rather than buffered next to whatever already holds the memory.
Reading Streams the multipart body part by part. A file over the per-file cap is cut off at the cap and marked too_large — it is never fully buffered. Nothing touches disk. The optional hints part is capped separately.
Kind detection Decides what each file is from its leading bytes, not from what the caller claimed. See below.
Orchestration Processes files concurrently (4 at a time by default) while returning results in request order. Emits one trace span, one set of metrics and one log line per file — kind, size, outcome, duration; never content.
Routing Maps kind to engine, applies the per-file timeout, and catches everything. Any exception an engine can raise becomes a per-file error entry, so one bad file cannot take down the batch. Only genuine client abandonment propagates.
Extraction The three engines below. They share one internal interface, so adding a fourth is a matter of registering it against the kinds it handles.

How the file type is decided

The declared content type is treated as a claim, not as truth — callers get it wrong, and a mislabelled file that silently took the wrong path would produce quietly wrong output. Detection reads the first bytes of the file instead:

SignatureResult
%PDFpdf
PNG signatureimage (image/png)
FF D8 FFimage (image/jpeg)
PK (a ZIP container — every Office file is one) docx / xlsx / pptx, disambiguated by the declared content type, falling back to the file extension
<!doctype or <html, or an HTML content type or extension html
none of the aboveper-file unsupported_type error

When the bytes and the declared type disagree, the bytes win and the file carries a warning saying so. The one case where the declaration matters is the ZIP family: a .docx, .xlsx and .pptx are all ZIP archives and cannot be told apart from their first bytes alone.

Extraction path 1 — PDF, DOCX, PPTX, HTML

LayoutEngine → Azure AI Document Intelligence, prebuilt-layout model, Markdown output.

These four kinds share one path because one managed model already handles all of them, including OCR. A scanned PDF and a digital PDF are the same call; the service does not need to detect which it has, and the caller does not need to care. The engine returns the model's Markdown, the page count (used for metrics), and any warnings the model itself reported.

The one failure worth singling out: when the service rejects a file as unreadable, that becomes a per-file corrupt error rather than an engine failure — a broken PDF is a fact about the file, not an incident.

Extraction path 2 — XLSX

SpreadsheetEngine → OpenXML, in process, no network call.

Spreadsheets deliberately do not go through the layout model. The point of a spreadsheet is its numbers, and a layout model returns rendered text — a cell displaying €3.75 or 3,750 would come back as exactly that string, and its true value would have to be guessed back out of the formatting. Instead the engine opens the workbook directly and reads each cell's stored value and declared type:

  • Numbers become JSON numbers, at full stored precision.
  • Date-formatted cells become ISO-8601 strings.
  • Booleans become true/false; shared strings are resolved to text.
  • Blank rows between populated ones are preserved, so section structure survives.
  • One table is produced per worksheet, each with both a Markdown rendering and the typed rows.

Anything odd degrades to a warning rather than a failure: a tab that turns out to be a chart is skipped and noted, a formula with no cached value is noted, a single cell whose stored text does not parse as the type it claims is kept as text and noted. Only a workbook that cannot be opened at all is a corrupt error.

Because this path is entirely local, it keeps working when the cloud engines are unreachable or not configured, and it is the fastest of the three by a wide margin.

Extraction path 3 — JPG, PNG

VisionEngine → a vision-capable model, one chat completion per image.

The image is sent to the model with a fixed system prompt that constrains it to observation only: list what is directly visible — objects, text, markings, labels, symbols, materials, colours, quantities — transcribe printed text and codes exactly, and do not identify product categories or infer purpose, quality or status.

That prompt is the "facts, never meaning" constraint made concrete at the one point in the system where a model could easily be induced to editorialise. It is treated as part of the contract, not as a tunable: changing its wording is a specification change, and a test pins it.

Purpose hints

The optional hints part lets a caller annotate individual files:

hints={"parts-list.xlsx":{"purpose":"bom"},"component.jpg":{"purpose":"photo"}}

Hints are parsed, validated against the known set and attached to the file as it moves through the pipeline; an unrecognised value is ignored with a warning rather than rejected. Today no engine reads them — they are the declared extension point for purpose-specific behaviour (a different vision prompt for a photo, a different table heuristic for a parts list) and are carried through the pipeline ready for it, but they do not currently change the output.

Deployment shape

  • Cluster-internal only. A ClusterIP service on port 8090
  • Degrades rather than disappears. An unreachable cloud engine yields engine_error for its file kinds while every other kind — notably the entirely local spreadsheet path — keeps working normally. A degraded dependency deliberately does not fail readiness: all replicas share the same upstream resources, so removing pods from the service would turn a partial outage into a total one.
  • But it does not start half-configured. Both cloud endpoints are required configuration, so a missing one is a boot failure rather than a per-file error. The alternative was a pod that started, passed both probes, and failed every file of the kinds it could not serve — visible only inside a caller's response body.

Health and observability

  • GET /health — readiness, reporting the last known state of each configured dependency from a background monitor, so no request ever waits on a cloud round-trip.
  • GET /live — liveness, deliberately blind to dependency state: an upstream outage must never restart a pod that is serving correctly.
  • GET /metrics — Prometheus exposition. Counters and histograms cover files, pages and bytes processed, per-file duration, duplicate submissions, and rejected or shed requests, tagged by file kind and outcome.
  • Traces: one span per file, tagged with kind, size and outcome — never a filename.
  • A startup connectivity check dials every configured endpoint before the service accepts traffic, so a misconfigured deployment fails loudly at boot instead of turning every document into a per-file error that only the caller ever sees.

5. Infrastructure requirements

The service is stateless, so what it needs from the platform is short: an Azure AI Foundry account exposing two model surfaces, an identity allowed to call them, and a Kubernetes namespace to run in. Everything listed here is provisioned outside the service — it consumes these, it creates none of them.

Models

Two models are required, and they are of different kinds. One is a built-in model addressed by name in the request; the other is a deployment that has to exist on the account before the service will serve a single image.

SurfaceWhat is requiredProvisioning
Document Intelligence
PDF · DOCX · PPTX · HTML		 The built-in prebuilt-layout model, at API version 2024-11-30 — the version pinned by the SDK the service is built against. OCR for scanned documents is part of that same model. None. A prebuilt model is a property of the service in a region, not something deployed into an account: it is named in the request body, has no deployment name, and there is no capacity to size. What must be true is that the region offers it.
Vision
JPG · PNG		 A vision-capable chat model that accepts image content parts on the chat-completions API. The service knows it only as a deployment alias — Foundry:DeploymentNameVision, shipped as model-eugo-docint-vision. A deployment must exist on the account under exactly that alias, with enough quota for the expected image volume. The service sends one completion per image.

The alias is deliberately decoupled from the model behind it: replacing or upgrading the vision model is an operation on the Foundry account alone — no image rebuild, no configuration change, no redeploy. The corollary is that no document can tell you which model is answering; the deployment is the source of truth.

The region gate. When one account serves both surfaces, both capabilities must be available in the same EU region — layout availability and vision-model availability each vary by region, and one account cannot straddle two. Two standalone resources remain a supported layout: the service reads two independent endpoint values and does not care whether they belong to the same account. One account is simply less to provision, secure and monitor.

The account

  • One account, two hostnames. A Foundry account publishes each API on its own FQDN — https://<resource>.cognitiveservices.azure.com/ for Document Intelligence, https://<resource>.openai.azure.com/ for the vision deployment. Neither is derivable from the other once custom subdomains, sovereign suffixes or private-endpoint DNS are in play, which is why configuration carries both as separate values.
  • A custom subdomain is mandatory, not optional. Entra ID authentication cannot use regional endpoints, and key-less operation is the intended production path.
  • An EU region, for every resource the service talks to.

Identity and access

  • Workload Identity — the production path. A federated identity for the pod's service account, plus a data-plane role on the account (Cognitive Services User or equivalent). The role has to cover both data planes: granting it on only one surfaces as a 403 on every file of the other kind, at runtime rather than at deploy time.
  • Or the account key. An account exposes one key pair — key1 and key2 are a rotation pair, not one key per API — so a single value authenticates both surfaces. It reaches the pod as configuration; the Helm chart accepts no credential material and creates no secret.
  • The choice is one decision for the account. With no key configured, both surfaces use the ambient managed identity, so they cannot end up on different authentication legs against the same resource.

Network

  • Outbound only, and only to the account. The service opens no other connection; it has no ingress, no certificate and no public DNS record of its own.
  • A private endpoint, where public access to the account is disabled. The cluster's VNet must be linked to the account's private DNS zones, and the endpoint must carry a record for every FQDN in use — the two hostnames this service reads sit on different suffixes, so a zone group covering one of them is not enough. A missing link is not a partial failure: neither cloud surface resolves, and the pod refuses to start.

Cluster

  • A namespace on AKS, a ClusterIP service on port 8090, and no ingress resource. Callers reach it by cluster-internal service name.
  • Two replicas, autoscaled. An HPA on CPU and memory takes it to six. Replicas are interchangeable — there is no session state and no leader.
  • A memory limit sized to the admission budget. Peak usage is roughly baseline plus the pod's in-flight byte budget, because every accepted file is held whole in memory for the duration of its request. The shipped chart requests 512 MiB and limits 2 GiB against a 1 GiB budget. Raising the budget or the per-file cap without raising the limit is how the pod gets OOM-killed.
  • A writable /tmp — load-bearing, not cosmetic. The container runs with a read-only root filesystem, and the spreadsheet path spills package parts to /tmp even though it reads the workbook from memory. Without that mount every XLSX request fails. Nothing short of a real pod catches it: the container build and the offline test suite both run on a writable filesystem, so the read-only root exists only once the chart is applied.
  • An image pull secret, since the image is published to a private registry.

What it does not require

Worth stating explicitly, because it is most of what an operator would otherwise plan for. There is no database, no blob container, no cache and no message broker — nothing to back up, nothing to migrate, nothing to restore. The only state a replica holds is the requests currently in flight, so scaling is adding pods and recovery is restarting them. A telemetry collector is optional: without one, counters are still readable from the scrape route, while traces and logs stay inside the pod. And there is no ingress, no TLS certificate and no public DNS record, because the service is not reachable from outside the cluster by design.

6. Configuration options

Every setting ships with a default in the image, except the two endpoints, which are environment-specific and therefore required from the operator. Configuration arrives in three layers, each overriding the one before it: the image's appsettings.json, then environment variables (a colon in a key becomes a double underscore — DocInt:MaxFileBytes is DocInt__MaxFileBytes), then, for a Kubernetes release, the Helm values that render those variables. A Helm value left empty renders no variable at all and leaves the image's default in force; the chart deliberately does not restate the defaults, so there is nothing for them to drift against.

All of it is validated at start-up. A missing, non-positive or mutually inconsistent value stops the pod at boot with a message naming the key — never on a live request, and never as a per-file error that only the caller ever sees.

Why the endpoints are required rather than optional. A blank endpoint used to be a supported mode, and the pod it produced looked healthy: it started, passed both probes, and answered a per-file error for every file of the kinds that endpoint served — a fault visible only inside a caller's response body and nowhere in the deployment. Requiring the values moves that failure to the boot, where it is loud. Supplying a value and dialling it stay separate decisions, though: a host that genuinely cannot reach the account still supplies the hostnames — they are addresses, not credentials — and turns off the start-up check below.

Combinations rejected at boot

Four rules relate settings to one another. Each is checked before the service accepts traffic, because each describes a pod that would otherwise look healthy and behave wrongly.

RuleWhy
MaxRequestFileBytes ≥ MaxFileBytes Otherwise a single maximum-size file could never be accepted.
Admission:BudgetBytes ≥ MaxRequestFileBytes + 1 MiB A budget smaller than the largest admissible request could never serve it — the request would ask for more permits than the pod owns.
DependencyCheck:TimeoutSeconds < IntervalSeconds Otherwise a slow probe overlaps the next tick.
StartupProbe:TotalTimeoutSeconds ≥ Attempts × AttemptTimeoutSeconds A budget smaller than the attempts it funds truncates the last one — which is the retry that matters, since the two before it have already failed.
